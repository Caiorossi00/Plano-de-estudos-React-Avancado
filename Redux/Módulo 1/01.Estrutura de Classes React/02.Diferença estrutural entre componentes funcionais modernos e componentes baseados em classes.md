A evolução do react substituiu o modelo mental baseado em instâncias (classes) por um modelo baseado em fluxos lineares e escopos léxicos (funções). Compreender a diferença estrutural entre essas duas abordagens é indispensável para transitar entre sistemas corporativos tradicionais e arquiteturas modernas, permitindo entender exatamente com o motor do react manipula o código em cada cenário.

1. Instância persistente vs execução volátil
A principal divergência estrutural reside no ciclo de vida da estrutura de dados em memória.
Um componente de classe é uma fábrica de objetos baseada em estado persistente. Quando inserido na árvore de renderização, o react aloca memória para uma instância específica dessa classe. Essa instância permanece viva no navegador enquanto o componente estiver na tela. Toda atualização de estado (this.setState) modifica atributos internos desse mesmo objeto, mantendo referências fixas em memória.
Em contrapartida, um componente funcional é uma rotina de execução volátil. Ele não possui uma instância. Toda vez que o estado ou uma propriedade muda, o react simplesmente reexecuta a função inteira do topo ao fim. As variáveis locais criadas dentro do corpo da função são destruídas e recriadas a cada ciclo. Para que dados como estados sejam retidos entre essas execuções, o react utiliza os hooks, que conectam a função volátil a uma lista encadeada de memória gerenciada internamente pelo motor do framework (fiber).

2. O escopo dos dados: O ponteiro this vs closures
Essa diferença de ciclo de memória altera drasticamente a forma como os dados são acessados e isolados dentro do código.
Nas classes, o acesso a propriedades e estados é dinâmico e amarrado ao ponteiro this. Quando você lê this.props.fornecedorId, você está acessando o valor contido na instância naquele exato milissegundo. Embora isso pareça simples, introduz problemas de concorrência e efeitos colaterais: se uma operação assíncrona demorar 3 segundos para responder e o usuário alterar os campos na tela nesse intervalo, o this.props terá mudado, e a função assíncrona lerá o dado novo, e não o valor do momento em que o gatilho foi disparado.
Nas funções, o comportamento baseia-se no conceito de closures (fechamentos léxicos). Como as propriedades são recebidas como argumentos da função (function Screen(props)), cada renderização possui seu próprio "ponto no tempo" (snapshot). Se uma função assíncrona captura uma propriedade em uma renderização, ela ficará eternamente presa àquele valor específico daquele ciclo, garantindo previsibilidade total e isolamento de dados.

3. Injeção de lógica: HOCs vs hooks customizados
A estrutura para reaproveitar lógica de negócio (como chamadas de API, controle de formulários e acesso ao redux) mudou de sentido vetorial.
No modelo de classes, a injeção ocorre de fora para dentro via Higher-order components (HOCs). Para dar novos poderes à tela, envolvemos o componente em funções decoradoras no final do arquivo. Estruturalmente, isso transforma seu componente em um consumidor passivo de propriedaeds agregadas, gerando um encapsulamento rígido e, muitas vezes, inflando a árvore de componentes com wrappers invisíveis (wrapper hell).
No modelo funcional, a injeção ocorre de dentro para fora via Hooks customizados. A função chama os hooks internamente, expondo a lógica diretamente no escopo do componente sem a necessidades de envelopar o código visual, eliminando intermediários estruturais e tornando o rastreamento de dados explícito e direto.
