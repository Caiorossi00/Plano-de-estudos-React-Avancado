Para dominar a escrita de código no padrão legado, não basta conhecer a anatomia da classe, é preciso compreender a coreografia do seu funcionamento. No react baseado em funções, o fluxo de atualizações é contínuo e linear. Nas classes, o fluxo é dividido em três fases estritas, mecânicas e sequenciais: Montagem (mounting), atualização (updating) e desmontagem (unmounting).
Entender quais métodos disparam em qual ordme, e como o motor do react processa as alterações do estado, é o conhecimento definitivo para decidir exatamente em qual linha de código inserir suas chamadas de API, formatações ou atualizações de formulário

1. A fase de montagem (mounting): O nascimento da tela
A montagem ocorre apenas uma vez no ciclo de vida do componente: quando ele é inserido pela primeira vez na árvore de componentes (DOM) do navegador. O ciclo síncrono executa os seguintes métodos nesta exata ordem:
1.constructor(props): aloca a instância na memória do navegador e amarra as propriedades iniciais
2.render(): o React executa o método para decodificar o JSX e gerar a primeira árvore do virtual DOM. Nenhuma alteração real no navegador aconteceu ainda.
3.componentDidMount(): o react insere o componente no DOM real do navegador e renderiza a interface para o usuário. Este é o método mais importante para a escrita da lógica inicial

O que escrever no componentDidMount:
Como este método roda exatamente após a tela aparecer, ele é o local obrigatório para:
- Disparar as actions do Redux/Ducks que buscam dados iniciais da API (como carregar uma lista de estados/cidades)
- Chamar o método this.props.initialize(dados) do redux-form se a tela já possuir dados prévios (como em uma tela de edição)
- Registrar ouvintes de eventos globais (como um listener de teclado ou conexões websockets)

2. A fase de atualização: A reatividade em cadeia
Esta fase é executada toda vez que o componente sofre uma alteração de dados. Uma atualização na classe pode ser engatilhada por três motivos: novas propriedades recebidas via HOCs (New Props), alteração de estado interno (this.setState) ou uma força de renderização (this.forceUpdate()).
Quando qualquer um desses gatilhos ocorre, o react inicia o seguinte fluxo:
1.shouldComponentUpdate(nextProps, nextState): É um método opcional que atua como um porteiro de performance. Ele recebe os próximos dados e deve retornar um booleano (true ou false). Se retornar false, o React interrompe o fluxo imediatamente e a tela não é re-renderizada, poupando processamento.
2.render(): O react reexecuta o método para recalcular o novo JSX baseado nos dados atualizados.
3.componentDidUpdate(prevProps, prevState): Executando imediatamente após o React aplicar as mudanças síncronas no DOM do navegador.

Como pensar e escrever dentro do componentDidUpdate:
Diferente do useEffect moderno que monitora variáveis automaticamente, o componentDidUpdate intercepta qualquer atualização na classe. Portanto, para evitar loops infinitos ou execuções desnecessárias, você deve realizar comparações manuais usando as propriedades e estados anteriores (prevProps e prevState).
Imagine o cenário comum no seu projeto: o usuário altera o campo "Estado" no formulário, e a tela precisa buscar as cidades daquele estado específico. A escrita desse código segue rigorosamente essa estrutura:

componentDidUpdate(prevProps, prevState) {
  // 1. Captura os valores do formulário vindos do Redux via HOC
  const estadoAtual = this.props.formValues?.estado;
  const estadoAnterior = prevProps.formValues?.estado;

  // 2. Compara se o ID do estado realmente mudou entre um render e outro
  if (estadoAtual !== estadoAnterior) {
    // 3. Executa a ação lógica apenas se houver mudança real
    this.fetchCidadesPorEstados(estadoAtual);
  }
}

Se você esquecer de envelopar a chamada da API dentro da condicional if (estadoAtual !== estadoAnterior), o fetchCidades vai atualizar o estado local da tela, o que vai disparar um novo componentDidUpdate, que chamará a API novamente, travando o navegador em um loop infinito de requisições.

3. A fase de desmontagem (Unmounting): A Limpeza da memória
A desmontagem ocorre quando o usuário navega para outra rota ou quando uma condição oculta o componente da tela. O reactexecuta um único método:
- componentWillUnmount()
Como os componentes de classe permanecem vivos na memória, se você registrou algum ouvinte global ou temporizador no componentDidMount, eles continuarão rodando em segundo plano mesmo se a tela sumir, gerando graves vazamentos de memória (memory leaks).

O que escrever no componentWillUnmount:
- Limpar timers (clearTimeout, clearInterval)
- Remover ouvintes de eventos globais (window.removeEventListener)
- Disparar ações de limpeza no redux (como resetar o estado de sucesso de um duck ao sair da tela)

4. Resumo do modelo mental para a escrita do código:
Ao olhar para um requisito de tela nova, mapeie os gatilhos visuais diretamente para estes três blocos:
- Preciso buscar os dados assim que a tela abrir? O código vai para componentDidMount()
- Preciso reagir à mudança de um campo ou propriedade do redux? O código vai dentro de um if dentro do componentDidUpdate(prevProps)
- Preciso limpar o estado ou cancelar um timer antes de mudar de página? O código vai dentro do componentWillUnmount().
Seguir essa divisão limpa o corpo da sua classe e garante que o motor do react processe as atualizações da sua tela com total previsibilidade e performance
