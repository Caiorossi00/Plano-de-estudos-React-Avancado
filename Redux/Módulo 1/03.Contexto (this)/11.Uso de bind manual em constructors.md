Antes da popularização das arrow functions como propriedade de classe, a forma mais comum de preservar o contexto de execução dos métodos em componentes react era realizar o binding manual dentro do constructor. Essa prática era praticamente obrigatória sempre que um método da classe fosse utilizado como callback, pois os métodos tradicionais não mantêm automaticamente sua associação com a instância do componente.

Para compreender por que isso era necessário, é importante lembrar como javascript trata métodos de classe. Um método radicional pertence ao protótipo da classe e seu valor de this é determinado apenas no momento da execução. Enquanto o método é chamado diretamente pela instância, como this.handleClick(), o contexto é preservado corretamente. Entretanto, quando esse mesmo método é passado como argumento para outra função ou utilizado como callback de um evento, ele deixa de ser executado pela instância e passa a ser chamado de forma independente. Nesse cenário, o this deixa de apontar para o componente, tornando indisponíveis propriedades como this.state, this.props e this.setState().

Foi para resolver esse problema que surgiu o uso do método bind(). Toda função em javascript possui esse método, cuja finalidade é criar uma nova função permanentemente associada a um determinado contexto de execução. Em componentes react, esse contexto é a própria instância representada por this.

class Usuario extends React.Component {
constructor(props) {
super(props);

        this.handleClick = this.handleClick.bind(this);
    }

    handleClick() {
        this.setState({ aberto: true });
    }

}

Nesse exemplo, o método handleClick continua sendo um método tradicional da classe, mas, durante a construção da instância, ele é substituído por uma nova função criada através de bind. Essa nova função permanece permanentemente vinculada ao componente, independentemente de onde venha a ser executada. Assim, quando for utilizada como callback de um botão ou passada para qualquer outra função, o this continuará representando corretamente a instância do componente.

O constructor era o local ideal para realizar esse processo porque ele é executado apenas uma vez, no momento em que o componente é criado. Dessa forma, o binding acontece uma única vez durante todo o ciclo de vida do componente, evitando que uma nova função seja criada a cada renderização. Essa abordagem preservava o componartilhamento dos métodos no protótipo da classe e garantia que cada instância tivesse apenas uma versão vinculada do método.

Apesar de funcionar corretamente, esse padrão apresentava algumas desvantagens. Em componentes com muitos manipuladores de eventos, o constructor acabava acumulando diversas chamadas de bind, tornando-se um bloco de código repetitivo e pouco relacionado à lógica de negócio da aplicação. Além disso, esquecer de realizar o binding de apenas um método era suficiente para provocar erros difíceis de identificar, principalmente quando o problema só aparecia durante a interação do usuário com a interface.

Foi justamente a verbosidade que impulsionou a adoção das arrow functions como propriedades de classe. Como elas capturam automaticamente o contexto léxico da instância, eliminaram a necessidade de escrever chamadas explícitas para bind, reduzindo a quantidade de código e diminuindo a chance de erros relacionados ao this.

Embora hoje seja menos comum encontrar componentes novos utilizando esse padrão, o binding manual continua aparecendo com frequência em aplicações react legadas. Entender seu funcionamento é importante porque ele não representa apenas uma técnica específica do react, mas uma solução para uma característica fundamental do javascript: métodos tradicionais não carregam seu contexto de execução consigo. O bind existe justamente para criar essa associação permanente, garantindo que um método continue operando sobre a instância correta do componente, independentemente de onde seja chamado.
