Uma das soluções mais utilizadas para evitar problemas com o this em componentes de classe é declarar métodos utilizando arrow functions como propriedades da própria classe. Essa abordagem tornou-se extremamente comum no react clássico porque elimina a necessidade de realizar o binding manual dos métodos no constructor, tornando o código mais simples e reduzindo uma das principais fontes de erro relacionadas ao contexto de execução.

Para entender por que isso funciona, é preciso lembrar que arrow functions possuem um comportamento diferente das funções tradicionais. Enquanto uma função comum determina o valor d ethis no momento em que é chamada, uma arrow function não cria seu próprio contexto. Em vez disso, ela captura o this do ambiente onde foi definida e o mantém durante toda a sua existência. Esse comportamento é conhecido como escopo léxico.

Nos componentes de classe, as propriedades da classe são incializadas durante a criação da instância do componente. Quando uma arrow function é atribuída a uma dessas propriedades, ela é criada já associada ao this daquela instância. Isso significa que, independemente de onde essa função seja executada posteriormente, ela continuará usando exatamente o mesmo contexto.

class Usuario extends React.Component {
handleClick = () => {
this.setState({ aberto: true });
};
}

Nesse exemplo, handleClick é criada durante a construção da instância e captura automaticamente o this do componente. Se essa função for passada como callback para um botão, um temporizador ou qualquer outra API do javascript, ela continuará acessando corretamente this.props, this.state e this.setState, pois seu contexto já foi definido no momento da criação.

Esse comportamento contrasta diretamente com os métodos tradicionais de classe. Um método declarado da forma convencional pertence ao protótipo da classe e somente descobre qual será seu this quando for executado. Se ele for chamado fora do contexto da instância, essa associação pode ser perdida, exigindo o uso de bind para restaurá-la. As arrow functions evitam esse problema porque não dependem da forma como são chamadas, elas carregam consigo o contexto léxico capturado durante sua definição.

Foi justamente essa característica que fez com que as arrow functions se tornassem o padrão predominante em aplicações react desenvolvidas antes das chegadas dos hooks. Em vez de escrever um constructor apenas para associar métodos à instância, bastava declará-los como propriedades da classe. O código ficava mais enxuto, mais legível e menos propenso a erros relacionados ao this.

Entretanto, essa conveniência possui uma consequência estrutural importante. Como a arrow function é criada durante a inicialização da instância, cada comportamento possui sua própria cópia daquela função. Diferentemente dos métodos tradicionais, que ficam armazenados no protótipo e são compartilhados entre todas as instâncias, as arrow functions ocupam espaço individualmente em cada objeto criado. Na maioria das aplicações react essa diferença de memória é pequena e dificilmente representa um problema prático, mas ela explica por que essa abordagem não substituiu completamente os métodos tradicionais no javascript orientado a objetos.

Mais importante do que decorar essa diferença é compreender a ideia de escopo léxico. O objetivo das arrow functions não é apenas reduzir código, mas garantir que o contexto do componente permaneça estável durante toda a execução da função. Essa previsibilidade foi uma das principais razões para sua adoção em comportamentos de classe e contribuiu para diminuir significativamente os erros envolvendo perda de contexto. Mesmo que os componentes funcionais tenham eliminado a necessidade de trabalhar com this, entender esse mecanismo continua sendo fundamental para interpretar e manter aplicações react legadas que utilizam intensivamente esse padrão.
