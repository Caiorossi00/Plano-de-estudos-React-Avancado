Em aplicações enterprise, a organização dos arquivos deixa de ser apenas uma questão de preferência pessoal e passa a ser um ferramenta para controlar a complexidade do sistema. À medida que uma aplicação cresce, surgem dezenas ou centenas de componentes, telas, reducers, actions, serviços, validações e integrações. Se esses arquivos forem organizados apenas pelo tipo técnico, encontrar tudo o que pertence a uma determinada funcionalidade pode se tornar difícil. O padrão ducks ajuda justamente a aproximar a estrutura física do projeto da estrutura funcional da aplicação.

Em uma organização tradicional de redux, é comum encontrar diretórios como actions, reducers e constantes. Um fluxo de usuários poderia ter seu reducer em reducers/usuarios.js, suas actions em actions/usuarios.js e seus tipos em constants/usuarios.js. Essa estrutura é simples no início, mas conforme o sistema cresce, cada nova funcionalidade aumenta a quantidade de arquivos espalhados pelos mesmos diretórios.

Em aplicações enterprise, isso pode gerar um problema de navegação. Para entender completamente uma funcionalidade, o desenvolvedor precisa percorrer diferentes camadas do projeto e relacionar mentalmente arquivos que estão fisicamente separados. O código continua funcionando, mas o custo cognitivo para compreendê-lo aumenta.

O ducks propõe uma organização orientada à funcionalidade. Em vez de agrupar arquivos pelo tipo de código que contêm, eles são agrupados pelo domínio ao qual pertencem. Assim, pode existir um módulo de usuários, outro de produtos e outro de pedidos, cada um contendo seu próprio fluxo redux. Dentro desses módulos ficam os types, actions e reducer relacionados àquela funcionalidade.

Essa organização também facilita a evolução incremental. Quando uma nova funcionalidade precisa ser adicionada, o desenvolvedor consegue identificar um espaço específico onde aquela responsabilidade deve existir. O módulo pode crescer internamente sem espalhar imediatamente novos arquivos por toda a estrutura global do projeto.

Em uma aplicação enterprise, porém, isso não significa colocar absolutamente tudo dentro de um único arquivo ou diretório. Uma funcionalidade pode possuir uma estrutura maior, separando componentes visuais, telas, serviços de API e regras específicas. O princípio é manter próximas as responsabilidades que pertencem ao mesmo domínio, enquanto responsabilidades diferentes continuam isoladas.

Por exemplo, uma funcionalidade de pedidos pode possuir uma estrutura conceitualmente semelhante a pedidos/, contendo o duck responsável pelo redux, uma screen responsável pela orquestração da tela, componentes visuais e serviços utilizados para comunicação com a API. Dessa maneira, ao trabalhar nessa funcionalidade, o desenvolvedor encontra a maior parte do contexto necessário em uma região relativamente próxima do projeto.

Essa organização também melhor a manutenção de código legado. Em sistemas antigos, frequentemente existem padrões diferentes convivendo no mesmo projeto, arquivos espalhados e dependências difíceis de rastrear. Uma estrutura orientada a funcionalidades permite evoluir partes específicas sem necessariamente reorganizar toda a aplicação. O objetivo não é tornar a arquitetura perfeita de uma vez, mas reduzir gradualmente o acoplamento e aumentar a previsibilidade.

Portanto, em aplicações enterprise, a organização estrutural deve facilitar principalmente três coisas: localização, compreensão e evolução. O padrão ducks contribui para isso ao agrupar types, actions e reducers de acordo com a funcionalidade que pertencem. A principal mudança de mentalidade é deixar de organizar o projeto apenas pela tecnologia utilizada e começar a organizá-lo também pelo domínio que o código representa. Isso torna a estrutura mais próxima da própria arquitetura do sistema e reduz o esforço necessário para entender e modificar cada fluxo.
