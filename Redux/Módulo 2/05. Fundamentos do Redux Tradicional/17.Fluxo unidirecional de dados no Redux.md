O redux foi criado para resolver um problema comum em aplicações de grande porte: à medida que a interface cresce, torna-se cada vez mais difícil acompanhar como os dados são modificados e quais componentes são responsáveis por essas mudanças. Em aplicações onde vários componentes compartilham informações, permitir que qualquer parte do sistema altere o estado diretamente torna o comportamento imprevisível e dificulta tanto a manutenção quanto a depuração. Para evitar esse cenário, o redux adota um princípio fundamental conhecido como fluxo unidirecional de dados.

A ideia central desse modelo é que toda alteração de estado deve seguir sempre o mesmo caminho. Não importa qual componente iniciou a mudança ou qual informação está sendo modfiicada, o percurso percorrido pelos dados nunca muda. Essa previsibilidade é um dos pilares do redux e permite compreender facilmente como uma alteração acontece dentro da aplicação.

O fluxo começa quando algum evento ocorre na interface. Esse evento pode ser um clique em um botão, o envio de um formulário, a resposta de uma requisição ou qualquer outra ação realizada pelo usuário ou pela própria aplicação. Entretanto, o componente não modifica a store diretamente. Em vez disso, ele apenas comunica sua intenção de alterar o estado através de uma action.

Essa action é enviada para a store utilizando a função dispatch(). O dispatch representa a porta de entrada de toda modificação no redux. Independentemente da origem da alteração, nenhuma mudança acontece sem passar por ele. A partir desse momento, a store encaminha a action para o reducer correspondente, responsável por interpretar aquela intenção e produzir um novo estado.

É importante perceber que o reducer não altera o estado existente. Sua responsabilidade é receber o estado atual e a action, calcular qual deve ser o próximo estado e retornar uma nova estrutura de dados. Somente após esse novo estado ser produzido é que a store substitui a versão anterior e notifica todos os componentes que dependem dessas informações. Os componentes conectados recebem os novos dados e o react realiza uma nova renderização da interface.

Esse processo pode ser resumido da seguinte forma:
Evento -> dispatch (action) -> Store -> Reducer -> Novo state -> Store atualizada -> Componentes -> Nova renderização

Observe que os dados sempre percorrem o mesmo caminho e nunca retornam ao ponto de origem para serem modificados diretamente. O componente não altera o estado, o reducer não atualiza a interface e a store não executa regras de negócio. Cada elemento possui uma responsabilidade específica dentro desse fluxo, o que reduz o acoplamento entre as partes da aplicação.

Esse modelo contrasta com arquiteturas baseadas em fluxo bidirecional, nas quais diferentes partes do sistema podem modificar o mesmo estado diretamente. Nesses casos, identificar quem alterou determinado dado pode se tornar uma tarefa difícil, especialmente em aplicações grandes. No redux, como toda alteração obrigatoriamente passa pelo dispatch e pelos reducers, existe sempre um caminho claro para investigar a origem de uma mudança.

Essa previsibilidade também favorece ferramentas de depuração. Como todas as alterações passam por um único fluxo, é possível registrar cada action disparada, visualizar como o estado era antes da atualização e comparar o resultado produzido pelo reducer. Ferramentas como o Redux DevTools exploram exatamente essa característica, permitindo acompanhar todo o histórico de mudanças realizadas durante a execução da aplicação.

É importante destacar que o fluxo unidirecional não significa que os dados viajam em apenas uma direção dentro da interface, mas que as alterações de estado seguem sempre um único percurso controlado. Os componentes continuam consumindo informações da store e exibindo esses dados ao usuário. Quando uma nova alteração é necessária, o processo recomeça desde o início, passando novamente pelo dispatch, pelos reducers e pela atualização da store.

Esse modelo de funcionamento torna o redux altamente previsível. Em vez de vários componentes disputarem o controle do estado da aplicação, existe um único fluxo responsável por coordenar todas as mudanças. Compreender esse percurso é fundamental para entender os demais conceitos do redux, como actions, reducers, middlewares e o padrão ducks, pois todos eles existem apenas para desempenhar um papel específico dentro desse fluxo unidirecional de dados.
