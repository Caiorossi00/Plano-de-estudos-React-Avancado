No redux, uma alteração de estado é dividida em duas reponsabilidades diferente: a action representa a intenção de que algo aconteça, enquanto o reducer determina como o estado deve ser transformado em resposta a essa intenção. Essa separação é fundamental para o funcionamento do redux porque impede que os componentes precisem conhecer diretamente a estrutura ou as regras de alteração do estado. 

Uma action é, essencialmente, um objeto javascript que descreve um acontecimento. Ela não altera a store por conta própria e também não contém necessariamente a lógica responsável por realizar a mudança. Seu papel é comunicar ao redux que determinado evento ocorreu. Por exemplo, uma aplicação pode produzir uma action como:
{
    type: 'USUARIO_SELECIONADO',
    payload: usuario
}

O campo type identifica o tipo de acontecimento, enquanto o payload pode transportar os dados necessários para que o redux consiga processá-lo. A Action pode ser criada diratemente pelo componente ou, como é mais comum em aplicações maiores, através de uma action creator. O importante é que ela represente uma intenção: "o usuário foi selecionado", "o formulário foi enviado" ou "a lista deve ser atualizada".

Quando essa action é enviada através de dispatch, ela percorre o fluxo do redux até chegar aos reducers. É nesse ponto que ocorre a separação entre intenção e transformação. O reducer recebe o estado atual e a action e decide qual deve ser o próximo estado. 

Um reducer tradicional costuma possuir uma estrutura semelhante a:
const reducer = (state = initialState, action) => {
    switch (action.type) {
        case 'USUARIO_SELECIONADO':
            return {
                ...state,
                usuario: action.payload
            };

        default:
            return state;
    }
};

A action apenas informou que um usuário foi selecionado e forneceu os dados relacionados. Quem decidiu o que fazer com essa informação foi o reducer. Ele identificou o type, acessou o payload e produziu uma nova versão do estado contendo o usuário selecionado. 

Essa distinção é importante porque o reducer não deve receber instruções específicas sobre como executar a alteração. A action não deveria dizer "substitua a propriedade usuário por este objeto". Ela apenas descreve o acontecimento. O reducer conhece a estrutura interna do estado e possui a responsabilidade de determinar como esse acontecimento deve ser representado dentro dele. 

Por isso, é mais correto pensar em uma action como um evento ou intenção e em um reducer como uma função de transformação de estado. O componente diz o que aconteceu, o reducer detemina qual consequência isso terá sobre o estado. 

Essa separação também mantém os componentes desacoplados da store. Um componente não precisa conhecer como os dados estão organizados nem quais propriedades precisam ser modificadas. Ele apenas dispara uma action. Isso permite alterar a estrutura interna do estado sem necessariamente modificar todos os componentes que utilizam aquele estado. 

É importante também diferenciar o termo "mutação" nesse contexto. Apesar de o reducer ser responsável por modificar o estado conceitualmente, ele não deve mutar diretamente o objeto de estado existente. O padrão tradicional do redux exige que o reducer produza uma nova estrutura de estado, preservando a anterior. Por ios, em vez de fazer algo como state.usuario = action.payload, utiliza-se uma atualização imutável através do spread operator, retornando um novo objeto. 

O fluxo completo pode ser entendido como: 
Evento -> Action -> dispatch() -> Reducer -> Novo estado 

Essa separação entre "o que aconteceu" e "como o estado deve reagir" é uma das principais razões pelas quais redux consegue manter um fluxo previsível. Actions podem ser registradas, reproduzidas e analisadas independentemente da implementação dos reducers, enquanto os reducers podem ser testados fornecendo um estado inicial e uma action e verificando qual novo estado foi produzido. Dessa forma, o redux transforma alterações de estado em um processo explícito: primeiro a aplicação desscreve um acontecimento, depois o reducer determina como esse acontecimento será refletido na store.
